\section{Archietttura del nuovo sistema}

Dopo aver raccolto e definito i requisiti per il nuovo sistema SRM attraverso varie riunioni con gli stakeholder e l'analisi del sistema attuale (SRP), è stato possibile progettare una nuova architettura per il sistema che permetta di soddisfare tali requisiti in modo efficiente e scalabile.


La nuova architettura proposta per il sistema SRM, riportata in figura \ref{fig:new-system-architecture}, è basata su un'architettura a microservizi, che consente una maggiore modularità, scalabilità e facilità di manutenzione rispetto all'architettura monolitica del sistema SRP attuale \cite{from_monolithic_architecture_to_microservices_architecture}.

\subsection{Componenti principali}
L'architettura del sistema SRM è composta dai seguenti componenti principali.

\subsubsection{Frontend}
Saranno sviluppati due frontend web separati per gli utenti finali e per gli amministratori di sistema, entrambi basati su Vue.js. Questi frontend comunicheranno con i servizi REST tramite API HTTP/HTTPS.

Grazie al fatto che la logica di business è stata spostata nei servizi REST, i frontend saranno più leggeri e facili da mantenere, permettendo una maggiore flessibilità nell'implementazione di nuove funzionalità e miglioramenti dell'interfaccia utente. Questo permette anche di integrare un'applicazione mobile in futuro, che potrà utilizzare le stesse API.

\subsubsection{Servizi REST}
REST (Representational State Transfer) è uno stile architetturale per la progettazione di servizi web che sfrutta i protocolli HTTP per la comunicazione tra client e server \cite{rest}. L'idea di base è che le risorse di un sistema (utenti, ordini, documenti, ecc.) vengano esposte attraverso un'interfaccia uniforme, tipicamente HTTP, usando \cite{rest}:
\begin{itemize}
    \item URL per identificare le risorse (\texttt{/api/catalog/actions/123/});
    \item Verbi HTTP per operare sulle risorse (\texttt{GET}, \texttt{POST}, \texttt{PUT}, \texttt{DELETE}, ...);
    \item Rappresentazioni delle risorse in formati standard (JSON, XML, ...).
\end{itemize}

I servizi REST saranno sviluppati utilizzando Django REST Framework, che offre un'architettura robusta e scalabile per la gestione delle API \cite{django_rest_framework}. 

Questi servizi saranno responsabili della logica di business, della gestione delle richieste degli utenti e dell'interazione con i database e altri componenti del sistema.

\subsubsection{Sistema di autenticazione e autorizzazione}
L'autenticazione e l'autorizzazione saranno gestite tramite la libreria PyElmecAuth sviluppata internamente, che si interfaccerà con il sistema di gestione delle identità aziendale per garantire un accesso sicuro e controllato ai servizi REST.

Sarà quindi necessario integrare in SRM un sistema di permessi granulare per garantire che gli utenti possano accedere solo alle risorse e alle funzionalità per cui sono autorizzati, basato sui ruoli definiti dall'Identity Provider aziendale.

\subsubsection{Sistema di caching}
Sarà necessario implementare un sistema di caching per migliorare le prestazioni del sistema e ridurre il carico sui database.

In particolare, verrano cachate le risposte delle chiamate a servizi esterni, come ad esempio le API di terze parti necessarie per validare alcuni campi, piuttosto che chiamate per recuperare informazioni sui clienti, per ridurre i tempi di risposta e migliorare l'esperienza utente. Il tempo di vita (TTL) delle cache dovrà essere configurabile in base alle esigenze specifiche di ogni tipo di dato.

\subsubsection{Message Broker e Task Queue}
Per gestire le operazioni asincrone e migliorare la scalabilità del sistema, verrà utilizzato un Message Broker (ad esempio RabbitMQ, Apache Kafka, Redis, \dots) in combinazione con una Task Queue (ad esempio Celery).

Questo è necessario in quanto il ciclo di vita delle SR è molto complesso e prevede molte operazioni che possono richiedere tempi di esecuzione lunghi \cite{azioni_gestione_srp}, come ad esempio l'invio di email, il mantenimento dei ticket HDA, l'integrazione con sistemi esterni, ecc. Utilizzando un sistema di messaggistica e code di task, queste operazioni potranno essere eseguite in background, senza bloccare il flusso principale dell'applicazione \cite{queue_model_relating_sync_async_communication}.

\subsubsection{Sistema di provisioning}.
Sarà anche necessario integrare un sistema di provisioning per eseguire gli script relativi alle SR e quelli di import delle anagrafiche direttamente nella rete dei clienti. Questo sistema dovrà essere sicuro, affidabile e scalabile, in modo da poter gestire un gran numero di richieste di provisioning contemporaneamente.

Elmec ha già un suo sistema di provisioning chiamato \textit{Provision Prime}, che verrà integrato con il nuovo sistema SRM per eseguire gli script in modo efficiente e sicuro.

\subsubsection{Sistema di monitoraggio e logging}
Per garantire la stabilità e l'affidabilità del sistema, sarà necessario integrare un sistema di monitoraggio e logging. Questo sistema permetterà di tracciare le performance del sistema, identificare eventuali problemi e analizzare i log per risolvere i bug. Saranno utilizzati strumenti come Prometheus, Grafana, New Relic o altri strumenti simili per implementare questo sistema.

Verranno tracciate sia le metriche di sistema (CPU, memoria, utilizzo del database, tempi di risposta delle API, ecc.) sia i log delle applicazioni (errori, avvisi, informazioni di debug, ecc.), in modo da avere sempre una visione completa dello stato del sistema, ed avere la possibilità di lanciare allarmi automatici in caso di problemi (e.g. se il numero di risposte andate in 500 (Internal Server Error) nell'ultima ora è >= 1\%).

\subsubsection{Sistema di containerizzazione e orchestrazione dei container}
Per facilitare il deployment, la scalabilità e la gestione del sistema, verrà utilizzato un sistema di containerizzazione (Docker) in combinazione con un sistema di orchestrazione dei container (Kubernetes).

Questo permetterà di isolare le diverse componenti del sistema, semplificare il processo di deployment e garantire una maggiore resilienza e scalabilità del sistema, tramite funzionalità come repliche, chronjob, scaling automatico dei pods, e così via \cite{kubernetes}.
