\chapter{Implementation of a Modular and Scalable Solution}\label{sec:chapter-implementation}
\sloppy

While Chapter \ref{ch:architectural-redesign} described in detail the requirements and the new architectural design for the new ServiceRequestManager (SRM) system, proposing targeted solutions to overcome the various technological and structural limitations of the legacy SRP system, this chapter marks the transition from the theoretical plan to practical realization, focusing on the concrete implementation of a modular and scalable solution.

The primary focus of this implementation lies in how the critical challenges described in the previous chapters were resolved. Specifically, it will be highlighted how the centralization of field management and configuration logic (and more generally of the catalog) on the backend eliminated the monolithic frontend and enabled a highly reusable three-level configuration system. The integration of the new execution and retrieval flow for master data through a message queue system will also be illustrated, which is essential for eliminating the dependency on the obsolete SRP Agent.

\subsubsection{Feature Branch Pipeline}

For feature branches, the pipeline executes automated checks for code quality, security, and compliance without building or deploying the application. The \texttt{complexity:xenon} stage measures code complexity through the Xenon static analyzer \cite{xenon}, identifying functions that might be difficult to maintain. The \texttt{formatter:black} stage verifies Python code compliance with PEP-8 conventions \cite{pep8}, while \texttt{linter:ruff} performs static analysis to detect errors and unsafe constructs.

Security scanning occurs through two Trivy stages: \texttt{libraries:trivy} identifies known vulnerabilities in dependencies against CVE databases \cite{trivy}, while \texttt{libraries:trivy-docker} scans deployment files and Kubernetes manifests for misconfigurations. The \texttt{SAST} stage uses Semgrep to detect security vulnerabilities such as SQL injection and XSS without code execution \cite{semgrep}.

\subsubsection{Live Environment Pipeline}

For main branches (\texttt{devel}, \texttt{quality}, \texttt{master}), the pipeline includes additional stages shown in Figure \ref{fig:live-env-pipeline-workflow}. The \texttt{base:python} stage builds the base Docker image containing Python dependencies, implementing layer separation to optimize build times through intelligent cache usage. The \texttt{test:pytest} stage executes the automated test suite against PostgreSQL 16, enforcing an 80\% code coverage threshold.

The \texttt{commitizen-release} stage manages automatic versioning using Commitizen, which analyzes commit history to determine version numbers according to Semantic Versioning and Conventional Commits conventions. This automated approach eliminates manual version management and ensures consistency in the release process.

Documentation stages generate OpenAPI/Swagger specifications using Django Spectacular and publish changelogs to the internal documentation platform.

The \texttt{deploy:argo-tags} stages manage automatic deployment through ArgoCD \cite{argocd}, a GitOps tool that synchronizes Kubernetes cluster state with Git-declared configurations. %Listing \ref{lst:argocd_deploy} shows the deployment trigger structure.

\subsubsection{Horizontal Pod Autoscaling}

The backend deployment implements Horizontal Pod Autoscaling (HPA) to dynamically adjust computational capacity in response to varying workload demands. The HPA configuration, shown in Listing \ref{lst:hpa_config}, establishes a scaling policy that maintains cluster efficiency while ensuring responsive service under load.

\begin{listing}[htbp]
\begin{minted}[
  linenos,
  tabsize=1,
  fontsize=\footnotesize,
  breaklines
]{yaml}
hpa:
  enabled: true
  minReplicas: 2
  maxReplicas: 5
  metrics:
    - type: "cpu"
      target_value: 70
\end{minted}
\caption{Horizontal Pod Autoscaler Configuration}
\label{lst:hpa_config}
\end{listing}

The HPA controller monitors CPU utilization across all backend pods, automatically scaling the replica count between 2 and 5 instances to maintain average CPU usage near 70\%. This threshold was calibrated through load testing to balance resource efficiency with headroom for traffic spikes: maintaining CPU utilization below saturation (typically 80-90\%) ensures that existing pods can handle transient load increases while new pods are provisioning \cite{nguyen2020horizontal}.

The minimum replica count of 2 provides baseline high availability, ensuring service continuity during pod failures or rolling updates, while the maximum of 5 prevents runaway scaling that could exhaust cluster resources or overwhelm downstream dependencies like the PostgreSQL database. The CPU-based metric was selected as the primary scaling signal because SRM workloads exhibit strong correlation between request volume and CPU consumption, as the system performs computationally intensive operations including JSON serialization, database query construction, and template rendering for dynamic field configurations.

Kubernetes implements the HPA control loop with a default evaluation period of 15 seconds, comparing current CPU utilization against the target threshold and calculating the required replica count using the formula \cite{nguyen2020horizontal}: 
$$
\texttt{desiredReplicas} = \lceil \texttt{currentReplicas} \times \frac{\texttt{currentMetricValue}}{\texttt{targetMetricValue}} \rceil
$$ 
Scale-up operations occur rapidly to accommodate load increases, while scale-down operations are deliberately dampened (5-minute stabilization window) to prevent thrashing during oscillating traffic patterns \cite{nguyen2020horizontal}.

The HPA enables the system to automatically expand capacity during peak hours while contracting during off-peak periods, optimizing infrastructure costs without compromising user experience through adequate headroom for unexpected load spikes.

\subsection{Scheduled Synchronization Jobs}

Kubernetes CronJobs maintain system alignment during the SRP-SRM coexistence period. The \texttt{sync-srp-catalog} job executes daily at 01:00 AM, importing catalog configurations from the SRP SQL Server database. The \texttt{sync-srp-sr-history} job runs at 02:00 AM, synchronizing service request execution history. The \texttt{import-directory-data} job triggers Ansible playbooks for master data export from customer Domain Controllers.

\section{Backend Service Implementation}

The backend service is the most critical component of the SRM architecture, responsible for managing application logic, processing service requests, and integrating with external systems. Its implementation was designed to ensure scalability, resilience, ease of maintenance, and a high degree of customization to accommodate the specific needs of clients.

\subsection{Technological Stack}

The backend leverages several key technologies that form the foundation of the system architecture.

\subsubsection{Core Framework}

The backend is built on \textit{Django} 6 with \textit{Django REST Framework} (DRF) 3.16, implementing a Model-View-Controller pattern where Django models handle data persistence, DRF viewsets manage business logic and request processing, and serializers handle data validation and transformation \cite{django}\cite{django_rest_framework}. This architecture was selected over alternatives like Go with GORM primarily due to development velocity considerations: Django's~comprehensive ecosystem of built-in components (ORM, authentication, admin interface) significantly reduces time-to-market compared to implementing equivalent functionality in Go. While Go offers superior raw performance, the anticipated load characteristics of SRM (primarily CRUD operations and orchestration) do not justify trading ecosystem maturity for performance gains.

\subsubsection{Asynchronous Processing}

\textit{Celery} with \textit{Redis} as the message broker implements the asynchronous task queue for service request execution and scheduled operations \cite{celery}. This producer-consumer architecture enables Django to publish tasks to Redis while dedicated worker processes consume and execute them independently, preventing long-running operations from blocking API responses. Celery was configured with thread-based workers optimized for I/O-bound operations (API calls, database queries, remote script execution coordination) rather than CPU-intensive processing.

\subsubsection{Message Queue System}
Redis was selected as the message broker over the more traditional RabbitMQ due to several compelling advantages in this deployment context. As an in-memory data structure store \cite{carlson2013redis}, Redis provides extremely low-latency message delivery, typically under 1ms for local network operations \cite{carlson2013redis}, which is very important for responsive task distribution in a system handling real-time service orchestration. Redis implements a publish-subscribe mechanism alongside its list-based queue structures, allowing Celery to leverage both \texttt{LPUSH}/\texttt{BRPOP} operations for reliable task queuing and pub/sub channels for worker coordination and result broadcasting \cite{carlson2013redis} \cite{redis_kafka_rabbitmq_comparison}.

The simplicity of Redis's operational model represents another significant benefit: unlike RabbitMQ's AMQP protocol with its complex exchange-binding-queue topology \cite{amqp}, Redis queues are straightforward data structures requiring minimal configuration and offering transparent introspection through standard Redis commands \cite{carlson2013redis}. This operational transparency proved valuable during development and debugging, as task queues could be inspected directly using \texttt{redis-cli} without specialized tools. Redis's built-in persistence mechanisms (RDB snapshots and AOF logs) provide adequate durability guarantees for this use case \cite{carlson2013redis}, where task loss tolerance is higher than in financial or transactional systems, while maintaining superior performance compared to RabbitMQ's disk-based persistence.

Furthermore, Redis's atomic operations and Lua scripting capabilities enable sophisticated task management patterns, such as atomic task deduplication using \texttt{SET NX} commands or complex priority queue implementations through sorted sets \cite{carlson2013redis}. The single-threaded event loop architecture of Redis eliminates concurrency concerns at the broker level, simplifying reasoning about task ordering and state consistency \cite{carlson2013redis}.

It should be noted that Celery's broker abstraction layer provides flexibility in this architectural choice: the application can be migrated to RabbitMQ post-deployment without requiring changes to task definitions or application logic, should operational requirements evolve to demand RabbitMQ's stronger delivery guarantees, more sophisticated routing patterns, or federation capabilities \cite{celery}. This broker-agnostic design principle proved prescient, as the production deployment ultimately transitioned to RabbitMQ to align with enterprise infrastructure standards while maintaining complete application compatibility \cite{celery}.
\subsubsection{Data Layer}

\textit{PostgreSQL} serves as the primary data store, selected for its robust ACID transaction guarantees, sophisticated query planning, and support for partial indexes and Common Table Expressions (CTEs) essential for hierarchical catalog queries. The application connects through \textit{PgBouncer}, a connection pooler that maintains persistent database connections and enables horizontal scaling of application pods without exhausting database connection limits \cite{pgbouncer}.

\textit{Memcached} implements distributed in-memory caching \cite{memcached}, specifically for responses from external financial and administrative systems (contracts, cost centers, project codes, server informations, ...). These external services exhibit high latency but return data with temporal stability, making them ideal candidates for caching with configurable TTL values.

\subsubsection{Remote Execution}

\textit{Ansible} orchestrates service request execution on customer infrastructure through agentless SSH/WinRM connections \cite{ansible}, eliminating the dependency on the legacy SRP Agent. Custom playbooks encapsulate provisioning workflows that currently wrap existing PowerShell scripts with a migration path toward native Ansible modules.

\subsubsection{Object Storage}

S3-compatible object storage (\textit{Ceph RGW} via MinIO API) manages master data exports and execution artifacts. Master data is exported to JSON in S3, then materialized in PostgreSQL for efficient querying, achieving sub-second response times compared to multi-second LDAP query latencies.

\subsection{Application Architecture}

The Django project is organized into six specialized applications following separation of concerns principles: \texttt{catalog/} manages the three-level configuration hierarchy; \texttt{integration/} handles external system integrations; \texttt{execution/} implements service request lifecycle management; \texttt{monitoring/} provides health checks; \texttt{directory\_data/} manages master data import; and \texttt{common/} contains shared utilities.

\subsection{Core Execution Workflows}

\subsubsection{Field Validation}

The validation system, centralized in \texttt{ServiceRequestValidationMixin}, implements comprehensive pre-submission validation. The architecture separates global validators (operating on complete field sets) from field validators (examining individual field-value pairs). Listing \ref{lst:validation_example} demonstrates the regex validation implementation.

\begin{listing}[htbp]
\begin{minted}[
  linenos,
  tabsize=1,
  fontsize=\footnotesize,
  breaklines
]{python}
def validate_field_value_regex(
    field: Field, value: str | None, **_kwargs
) -> None:
    if field.validation_regex and value:
        if not re.fullmatch(field.validation_regex, value):
            raise serializers.ValidationError({
                "fields_validation": [
                    f"The value '{value}' does not match pattern"
                ]
            })
\end{minted}

Validation progresses through multiple layers: syntactic validation via regex patterns, configuration-based validation, option validation for select fields, and specialized validation for external endpoints. The framework implements error aggregation, continuing validation after detecting failures to accumulate all errors before returning consolidated responses.

\section{Frontend Application Implementation}

The SRM frontend comprises two Vue.js 3 applications: an end-user service request creation interface and an administrative configuration platform.

\subsection{Technology Stack}

Both applications leverage Vue 3 Composition API with TypeScript for type safety \cite{vue3}. State management is implemented through Pinia \cite{pinia}, and the component architecture utilizes a custom design system library (ElmecUIX).

\subsection{Service Request Creation Interface}

The end-user interface implements a dynamic form builder rendering forms based on backend API responses. A single GET request retrieves complete action definitions including resolved field configurations. Listing \ref{lst:vue_validation} shows the client-side validation rules generation.

\begin{listing}[htbp]
\begin{minted}[
  linenos,
  tabsize=1,
  fontsize=\footnotesize,
  breaklines
]{typescript}
const formRules = computed(() => {
  const rules: Record<string, any[]> = {}
  
  for (const af of action.value.action_fields) {
    const fieldName = af.field.name
    if (!af.mandatory && !af.validation_regex) continue
    
    rules[fieldName] = []
    if (af.mandatory) {
      rules[fieldName].push({
        required: true,
        message: t("general.required")
      })
    }
    if (af.validation_regex) {
      rules[fieldName].push({
        validator: (rule, value, callback) => {
          const regex = new RegExp(af.validation_regex)
          if (!regex.test(value)) {
            callback(new Error(af.validation_regex_message))
          } else {
            callback()
          }
        }
      })
    }
  }
  return rules
})
\end{minted}
\caption{Dynamic Form Validation Rules in Vue.js}
\label{lst:vue_validation}
\end{listing}

The component architecture separates concerns through parent-child relationships. Field dependency resolution is implemented through reactive watchers monitoring form data changes. External API option caching minimizes redundant backend calls through URL tracking and result storage.

\subsection{Administrative Configuration Platform}

The administrative interface (in design phase) will provide CRUD operations for managing catalog hierarchy components with form-based editors, visual representation of override relationships, and preview functionality enabling administrators to test configurations before deployment.

The frontend architecture achieves dynamic, configuration-driven interfaces that adapt to catalog changes without code modifications, enabling rapid iteration on service request workflows.
